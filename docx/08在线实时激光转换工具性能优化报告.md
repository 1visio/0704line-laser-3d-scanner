# 在线实时线激光转换工具性能优化报告

## 摘要

针对在线线激光三维测量工具在相机连续采集条件下存在的处理吞吐不足、图像显示卡顿及 Qt 主线程事件积压等问题，本文对激光中心提取、叠加图生成、线程间信号传递、相机数据复制和无损录制五个环节进行了分阶段分析与优化。系统默认工作参数为 Mono8 像素格式、1200 us 曝光时间、2448 px × 300 px 硬件感兴趣区域（Region of Interest, ROI）以及 centroid 激光中心提取算法。

优化首先利用前缀和方法重构 centroid 算法中的段内加权修正过程，使该过程从逐点 Python 循环转化为 NumPy 向量化计算；随后将激光中心叠加图由“每个处理帧均生成”调整为“显示时按需生成并缓存”；进一步对处理结果和统计信息的 Qt 跨线程信号进行限频；最后将 MVS SDK 图像缓冲区到 NumPy 数组的两次复制缩减为一次复制，并对无损录制编码方案进行了吞吐与存储开销评估。

在同一张 2448 px × 300 px 实拍 ROI 图像、约 2443 个有效激光中心点的条件下，纯处理流水线的中位耗时由约 29.05 ms 降至 4.72～6.13 ms，对应理论处理能力由约 34 frame/s 提升至 163～212 frame/s。真实相机在线运行时，界面观测到采集帧率约 126.7 frame/s、处理帧率约 106.3 frame/s、显示帧率约 12.6 frame/s，单帧处理耗时约 5.0 ms。实验结果表明，优化后算法处理能力已不再构成默认采集参数下的主要吞吐瓶颈，同时保留了测量点数量、校准坐标变换、显示结果及无损录制行为。

**关键词：** 线激光；实时三维测量；激光中心提取；向量化；异步流水线；Qt；性能优化

---

## 1. 研究背景与优化目标

在线线激光三维测量系统需要连续完成图像采集、激光条纹中心提取、像素坐标恢复、三维重建、图形显示及原始帧录制。上述任务具有不同的计算特征：图像采集主要受相机曝光、传感器读出及 GigE 链路限制；激光中心提取属于像素级数值计算；三维重建属于点级矩阵计算；图像叠加和三维显示则受到 GUI 主线程刷新能力限制。

优化前，在默认 ROI 下相机采集帧率明显高于算法处理帧率，导致容量为 1 的最新帧缓冲区频繁覆盖旧帧。该机制能够避免延迟无限累积，但较低的处理吞吐仍会减少单位时间内完成三维重建的有效截面数量。因此，本次工作的主要目标如下：

1. 在不改变 centroid 算法数学定义和有效测量点数量的条件下降低激光中心提取耗时。
2. 将测量计算与可视化开销解耦，避免为未显示的处理结果生成图像叠加数据。
3. 控制工作线程向 Qt 主线程发送事件的频率，避免 GUI 事件队列积压。
4. 减少相机 SDK 缓冲区的数据复制次数，同时保证帧数据在 SDK 缓冲释放后的所有权安全。
5. 评估无损录制的编码吞吐、存储开销及其对在线处理实时性的影响。
6. 通过单元测试、微基准和完整并行基准验证优化的正确性及实时性贡献。

## 2. 系统配置与处理流水线

### 2.1 默认实验配置

| 参数 | 默认值 |
|---|---:|
| 相机型号 | MV-CS050-60GM |
| 像素格式 | Mono8 |
| 曝光时间 | 1200 us |
| 增益 | 0 dB |
| ROI 水平偏移 | 0 px |
| ROI 垂直偏移 | 880 px |
| ROI 宽度 | 2448 px |
| ROI 高度 | 300 px |
| 激光中心提取算法 | centroid |
| 单帧像素数 | 734400 pixel |
| Mono8 单帧原始数据量 | 734400 byte，约 0.734 MB |

当采集帧率为 126.7 frame/s 时，未计协议开销的图像有效载荷约为：

\[
B = 2448 \times 300 \times 1 \times 126.7
  \approx 93.05\ \text{MB/s}.
\]

因此，硬件 ROI 不仅减少了算法输入规模，也显著降低了相机传输和主机内存带宽需求。与 2448 px × 2048 px 全幅图像相比，默认 ROI 的像素数量约缩小 6.83 倍。

### 2.2 异步处理结构

在线系统由以下四个主要执行单元构成：

1. **相机采集线程：** 调用 MVS SDK 获取图像，将原始帧送入录制队列和最新帧缓冲区。
2. **最新帧缓冲区：** 容量固定为 1。当处理线程尚未取走上一帧时，新帧覆盖旧帧，以保持低延迟。
3. **算法处理线程：** 对最新帧依次执行激光中心提取、ROI 坐标恢复和三维重建。
4. **Qt 主线程：** 按受控频率显示原始图像、激光中心、三维点云、二维截面及实时统计信息。

录制器使用独立后台线程从有界队列读取原始帧并执行无损文件写入。因此，正常情况下图像编码和磁盘写入不会直接阻塞相机采集线程。

该结构的核心设计原则是“采集、计算和显示解耦”。三个帧率分别表征不同阶段：

- **采集 fps：** 相机线程实际取得图像的速率。
- **处理 fps：** 完成激光提取和三维重建的速率。
- **显示 fps：** Qt 主线程真正完成可视化刷新的速率。

显示帧率低于采集帧率并不等价于相机卡顿。对于测量系统，处理帧率和数据时间戳比显示帧率更能反映有效测量吞吐，而显示侧只需保证交互流畅且显示最新状态。

## 3. 优化前的性能瓶颈

在默认 ROI 实拍图像上，优化前单帧处理的典型耗时构成为：

| 模块 | 中位耗时 | 占比 |
|---|---:|---:|
| centroid 激光中心提取 | 20.655 ms | 约 71.1% |
| 三维重建 | 0.606 ms | 约 2.1% |
| 叠加图与结果组装 | 7.775 ms | 约 26.8% |
| 总处理时间 | 29.050 ms | 100% |

由此可见，主要瓶颈并不在三维重建，而在 centroid 算法内部的段内修正以及逐点绘制叠加图。总耗时 29.05 ms 对应约 34.4 frame/s 的理论处理上限，明显低于相机约 120 frame/s 以上的采集能力。

从输入规模分析，设图像像素数为 \(P=H\times W\)，提取到的激光中心点数为 \(N\)，centroid 修正窗口宽度为 \(K\)，则主要计算复杂度可概括为：

- 背景估计和逐列峰值搜索：约为 \(O(P)\)，高斯滤波常数项与核尺寸有关。
- 局部灰度重心：约为 \(O(Wr)\)，其中 \(r\) 为重心窗口半径。
- 原段内修正：理论上为 \(O(NK)\)，且由 Python 逐点循环执行。
- 三维重建：\(O(N)\)，主要由 NumPy 向量化矩阵运算完成。
- 叠加图生成：\(O(P+N)\)，其中 \(N\) 次 `cv2.circle` 由 Python 循环发起。

在本系统中，\(N\) 约为 2443。虽然修正窗口 \(K\) 为常数，但 Python 循环中重复进行切片、求和和函数调用，产生了显著的解释器开销。

## 4. centroid 段内修正向量化

### 4.1 原始计算方法

centroid 算法首先计算每列激光峰值及局部灰度重心，并按连续性将候选点划分为若干线段。为抑制局部抖动，原实现对每个线段内的第 \(i\) 个垂直坐标 \(v_i\) 进行加权邻域修正。对比度权重定义为：

\[
w_i = \frac{c_i}{\max(c)+\varepsilon} + 10^{-4},
\]

其中 \(c_i\) 为局部对比度。给定半径为 \(r\) 的窗口，第 \(i\) 点的局部估计为：

\[
\hat{v}_i =
\frac{\sum_{j=L_i}^{R_i-1} w_jv_j}
     {\sum_{j=L_i}^{R_i-1} w_j}.
\]

修正量还需满足最大位移约束：

\[
\Delta v_i = \operatorname{clip}
(\hat{v}_i-v_i,-\Delta v_{\max},\Delta v_{\max}).
\]

原代码针对每个点分别执行窗口切片和两次求和，导致同一权重和加权坐标被重复访问。

### 4.2 前缀和向量化方法

优化后分别构造权重前缀和及加权坐标前缀和：

\[
S_w(k)=\sum_{j=0}^{k-1}w_j,
\qquad
S_{wv}(k)=\sum_{j=0}^{k-1}w_jv_j.
\]

任意窗口 \([L_i,R_i)\) 的求和可由两次前缀和相减得到：

\[
\hat{v}_i=
\frac{S_{wv}(R_i)-S_{wv}(L_i)}
     {S_w(R_i)-S_w(L_i)}.
\]

所有点的左右边界、局部估计和截断修正均通过 NumPy 数组一次性计算。该实现将窗口求和由重复计算转化为线性前缀扫描，整体复杂度由 \(O(NK)\) 降为 \(O(N)\)，同时消除了逐点 Python 循环。

对应实现位于：

- [`laser/backends.py`](../laser_measurement_tool/laser/backends.py) 中的 `_correct_segment_v()`。

### 4.3 正确性与性能结果

向量化结果使用独立的旧版逐点公式作为参考，通过逐元素数值一致性测试。实测最大绝对误差约为 \(1.97\times10^{-11}\) pixel，该差异仅来自浮点累加次序变化，不会影响激光点有效性判断或三维重建结果。

| 指标 | 优化前 | 向量化后 |
|---|---:|---:|
| 单独段内修正中位耗时 | 16.418 ms | 0.043 ms |
| centroid 提取中位耗时 | 20.655 ms | 约 4.52 ms |
| 完整单帧中位耗时 | 29.050 ms | 12.848 ms |
| 理论处理能力 | 约 34.4 frame/s | 约 77.8 frame/s |
| 有效三维点数 | 2443 | 2443 |

该阶段为本次优化中贡献最大的单项措施，并且没有通过减小 ROI、降低点密度或关闭修正功能换取速度。

## 5. 叠加图延迟生成

### 5.1 原始问题

处理流水线原先在每个完成重建的帧上执行以下操作：

1. 将灰度图转换为 RGB 图像；
2. 遍历全部激光中心点；
3. 对每个中心点调用一次 `cv2.circle` 绘制绿色标记；
4. 将叠加图随 `FrameResult` 传递至 Qt 主线程。

约 2443 次逐点绘制的中位耗时为 7.78～8.02 ms。由于实际显示帧率只有约 10～13 frame/s，大量已经生成的叠加图并未真正显示，其计算和内存分配属于无效开销。

### 5.2 按需生成与缓存

优化后，算法流水线仅保存以下必要数据：

- 原始相机帧；
- 恢复到全传感器坐标的激光中心；
- 三维点云和二维截面；
- 各阶段耗时与校准元数据。

`FrameResult.overlay_rgb` 被实现为延迟属性。只有当“图像与条纹”页面准备刷新激光中心预览时，系统才进行以下操作：

1. 根据 ROI 偏移量将全传感器坐标还原为 ROI 局部坐标；
2. 生成 RGB 叠加图；
3. 将结果缓存在当前 `FrameResult` 中；
4. 同一结果的后续访问直接复用缓存。

这种设计保持了 `result.overlay_rgb` 的外部调用接口，避免破坏已有脚本，同时使三维页面和二维截面页面不再承担图像叠加成本。

对应实现位于：

- [`online/models.py`](../laser_measurement_tool/online/models.py) 中的 `FrameResult.overlay_rgb`；
- [`online/pipeline.py`](../laser_measurement_tool/online/pipeline.py) 中的 `render_overlay()`。

### 5.3 性能贡献

延迟生成后，纯处理流水线中位耗时进一步由 12.85 ms 降至约 4.72～6.13 ms。不同测试轮次受操作系统调度和同机负载影响存在波动，但理论处理能力稳定高于当前相机约 123～127 frame/s 的采集速率。

单次叠加图生成仍需约 7.85～7.98 ms，但该成本只按显示刷新频率产生。以 75 ms 显示周期计算，叠加图最多约生成 13.3 次/s，而不是按每个处理帧生成。因此，该优化本质上不是缩短绘图本身，而是消除不可见帧上的冗余绘图。

## 6. Qt 跨线程信号限频

### 6.1 事件积压机理

算法处理线程通过 Qt queued signal 将结果发送至主线程。若处理线程以 100 frame/s 以上的速率发送结果，而界面最多只能以约 13 frame/s 完成刷新，则主线程事件队列可能不断累积。即使界面槽函数内部再次检查刷新间隔，Qt 仍需对每个已投递事件完成排队、参数引用和槽函数调用。

这种情况会产生以下影响：

- 主线程用于无效槽调用的时间增加；
- 用户操作、窗口缩放和标签页切换的响应变慢；
- 显示内容可能滞后于最新测量结果；
- 高频统计文本更新造成额外布局和重绘开销。

### 6.2 限频策略

优化后，控制器始终以最高可用速率处理最新帧并更新 `last_result`，但对 UI 信号设置独立周期：

| 信号 | 最小发送周期 | 最大理论频率 | 用途 |
|---|---:|---:|---|
| 原始图像信号 | 50 ms | 20 Hz | 原始相机预览 |
| 处理结果信号 | 75 ms | 13.3 Hz | 激光、三维和二维显示 |
| 统计信息信号 | 250 ms | 4 Hz | fps、耗时和覆盖计数 |

限频只作用于“向 Qt 发送结果”，不作用于相机采集、算法计算、最新结果保存及后台录制。因此，处理 fps 不会被限制为 13.3 frame/s，快照和后续计算仍可使用控制器中的最新结果。

对应实现位于：

- [`online/controller.py`](../laser_measurement_tool/online/controller.py) 中的 `RESULT_EMIT_INTERVAL_S`、`STATS_EMIT_INTERVAL_S` 和 `_emit_stats_if_due()`。

### 6.3 实测结果

在 2 s、2448 px × 300 px、模拟 123 frame/s 输入的测试中，采集和处理分别保持约 113.0 frame/s 和 112.5 frame/s；Qt 处理结果信号约为 13.0 Hz，统计信号约为 4.5 Hz。该结果证明信号限频没有限制后台处理吞吐，同时显著减少了主线程事件数量。

## 7. MVS 相机帧复制优化

### 7.1 原始复制路径

MVS SDK 返回的 `pBufAddr` 指向 SDK 管理的图像缓冲区。调用 `MV_CC_FreeImageBuffer()` 后，该缓冲区不能继续被 NumPy 使用，因此系统必须在释放前复制图像数据。

原实现包含两次复制：

1. `ctypes.string_at()` 将 SDK 缓冲区复制为 Python `bytes`；
2. NumPy 从 `bytes` 建立视图后再次调用 `.copy()`，生成自有数组。

虽然该方法安全，但产生了不必要的中间 `bytes` 对象和第二次整帧复制。

### 7.2 单次复制方法

优化后预先分配连续的 NumPy 数组，再使用 `ctypes.memmove()` 将 SDK 缓冲区直接复制到数组自有内存。随后即可安全调用 `MV_CC_FreeImageBuffer()`。新路径具有以下性质：

- 只进行一次整帧内存复制；
- NumPy 数组具有独立所有权；
- SDK 缓冲区释放后图像内容保持有效；
- Mono8 与未打包 Mono12 数据布局保持不变。

对应实现位于：

- [`online/mvs_camera.py`](../laser_measurement_tool/online/mvs_camera.py) 中的 `_copy_frame_payload()`。

### 7.3 性能结果

| 复制方式 | 中位耗时 | P95 耗时 |
|---|---:|---:|
| `string_at()` + NumPy `.copy()` | 0.374 ms | 0.448 ms |
| NumPy 预分配 + `memmove()` | 0.201 ms | 0.246 ms |

单帧约节省 0.17 ms。该收益小于算法向量化和叠加图延迟生成，但属于稳定且不改变数据内容的底层优化。测试还验证了源缓冲区被修改后 NumPy 图像保持不变，从而确认其内存所有权安全。

## 8. 无损录制编码评估

### 8.1 编码方案对比

录制模块默认将 Mono8 图像保存为无损 PNG，将 Mono12 图像保存为 TIFF。针对 Mono8 实拍帧，对 PNG 编码策略进行了比较：

| 方案 | 单帧耗时 | 单帧大小 | 评价 |
|---|---:|---:|---|
| OpenCV 默认 PNG | 约 6.78 ms | 约 292 KB | 当前方案 |
| PNG 零压缩 | 约 6.32 ms | 约 736 KB | 编码略快，文件显著增大 |

零压缩只能节省约 0.46 ms，却使单帧文件增大约 2.52 倍。按 123 frame/s 估算，默认方案的输出数据量约为 36 MB/s，而零压缩接近 90 MB/s。后者会显著提高磁盘带宽、存储容量和文件系统缓存压力。

### 8.2 完整录制吞吐

使用实拍 ROI 图像按 123 frame/s 节奏连续写入 200 帧时，实验结果为：

- 保存帧数：200/200；
- 录制队列丢帧：0；
- 实际录制吞吐：约 122.7 frame/s；
- 200 帧 PNG 总大小：58462600 byte，约 58.5 MB。

进一步将相机采集、centroid 提取、三维重建和 PNG 录制同时运行，得到：

- 采集帧率：约 122.3 frame/s；
- 处理帧率：约 121.7 frame/s；
- 录制帧数：200/200；
- 录制队列丢帧：0；
- 最新帧缓冲覆盖：0。

因此，在默认 ROI 和当前硬件环境下，现有无损 PNG 编码能够跟上相机采集，不需要牺牲存储效率换取有限的编码加速。本阶段最终保留原编码策略。

需要注意，录制队列容量为 64。按 Mono8 原始帧计算，其最大图像载荷约为 47 MB，可吸收约 0.5 s 的短时磁盘抖动，但不能代替持续写入能力。若后续改用全幅 ROI、多相机或更高位深，应重新评估磁盘持续写入速度和队列容量。

## 9. 综合性能结果

### 9.1 分阶段贡献

| 优化阶段 | 纯处理流水线中位耗时 | 理论处理上限 | 主要贡献 |
|---|---:|---:|---|
| 优化前 | 29.05 ms | 约 34.4 frame/s | 基准 |
| 段内修正向量化 | 12.85 ms | 约 77.8 frame/s | 消除逐点窗口求和 |
| 叠加图延迟生成 | 4.72～6.13 ms | 约 163～212 frame/s | 消除不可见帧的绘图 |
| Qt 信号限频 | 流水线耗时基本不变 | 后台处理保持全速 | 降低 GUI 事件负载 |
| 相机单次复制 | 每采集帧再节省约 0.17 ms | 小幅提升采集侧余量 | 消除一次内存复制 |

理论处理上限由单帧处理耗时的倒数计算，仅表示在离线、单阶段连续运行条件下的计算能力。真实在线帧率还受相机周期、线程调度、内存带宽、Qt 绘制、系统负载和录制状态影响，因此不应直接将理论值视为相机实测帧率。

### 9.2 真实相机在线结果

在默认配置下，当前界面观测结果为：

| 实时状态参数 | 观测值 |
|---|---:|
| 采集 fps | 126.7 |
| 处理 fps | 106.3 |
| 显示 fps | 12.6 |
| 最近单帧处理耗时 | 5.0 ms |
| 相机帧号缺口 | 5 |
| 最新帧缓冲覆盖 | 2733 |

上述结果说明：

1. 相机能够稳定输出 120 frame/s 以上的硬件 ROI 图像。
2. 最近单帧算法耗时约 5.0 ms，对应的瞬时计算能力约为 200 frame/s，算法核心已具备高于相机采集频率的能力。
3. “处理 fps”是从运行开始累计计算的实际吞吐，受启动阶段、线程调度、显示和系统竞争影响，因此可能低于由最近单帧耗时计算的瞬时上限。
4. “显示 fps”由 Qt 刷新周期主动限制在约 13 frame/s，目的是保证交互响应；它不表示相机或算法只能运行 12.6 frame/s。
5. “相机帧号缺口 5”表示相机帧编号中检测到的缺失量，应作为链路或驱动层丢帧指标观察。
6. “最新帧缓冲覆盖 2733”表示采集线程产生新帧时，旧帧尚未被处理线程取走。该计数属于低延迟策略的主动覆盖，不等同于相机网络丢包。只要系统使用最新截面而非要求逐帧离线复现，该策略可以防止延迟随运行时间增长。

对于必须保留每一个三维截面的扫描任务，不能仅依赖容量为 1 的最新帧缓冲区，而应使用足够容量的处理队列、相机触发同步或直接录制原始帧后离线重建。当前在线模式优先保证实时观察和最新结果低延迟。

## 11. 局限性与后续建议

虽然默认配置下的实时性能已满足当前使用需求，仍需注意以下边界条件：

1. 本报告主要针对 Mono8、2448 px × 300 px ROI 和 centroid 算法。切换到全幅图像、Mono12 或 Steger 类算法后，应重新建立基准。
2. 激光叠加图仍采用逐点 `cv2.circle`，但由于已经按显示频率延迟生成，其优化优先级较低。若未来需要 30 Hz 以上叠加预览，可考虑使用向量化像素标记或 GPU 绘制，并重新比较显示效果。
3. 当前最新帧缓冲区以低延迟为优先目标，不保证每个采集帧都完成三维重建。若测量任务要求完整时间序列，应增加“逐帧处理模式”并明确队列积压告警。
4. PNG 编码在当前 ROI 下能够持续运行，但全幅、高位深或多相机录制可能成为磁盘瓶颈。可进一步评估无压缩 TIFF、分块二进制容器或高速 NVMe 顺序写入方案。
5. 实时 fps 为运行期统计量，正式实验应记录测试时长、CPU 型号、磁盘型号、网卡参数、MVS 驱动版本及后台负载，以提高性能结果的可重复性。

## 12. 总结

本次工作围绕在线线激光测量系统的完整数据路径开展性能优化。首先，通过前缀和向量化消除了 centroid 段内修正中的主要 Python 循环，使激光中心提取耗时下降约 16 ms；其次，通过叠加图按需生成，使不可见帧不再承担约 8 ms 的绘图成本；随后，通过 Qt 信号限频将后台高频计算与前台低频显示解耦，避免主线程事件积压；最后，通过 NumPy 预分配和单次 `memmove` 降低相机帧复制开销，并验证当前无损 PNG 录制能够在约 123 frame/s 下无队列丢帧持续运行。

在默认 2448 px × 300 px 硬件 ROI 下，纯处理流水线中位耗时由约 29.05 ms 降至 4.72～6.13 ms，测量点数和算法数学定义保持不变。真实相机运行结果进一步表明，系统已经能够实现约 126.7 frame/s 的图像采集和约 106.3 frame/s 的在线三维处理，并以约 12.6 frame/s 的受控频率进行稳定显示。由此可认为，当前版本已经从“算法处理受限”转变为“相机、线程调度与使用模式共同决定实际吞吐”的状态，满足在线实时观察和高频截面转换的应用需求。
